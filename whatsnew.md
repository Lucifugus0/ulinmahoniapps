| 2026-05-07 | Parking — design pivot to one-row-per-renewal + full `t_parking` reconstruction (`t_parking`) | Architecture change after the Kost 2 audit revealed that the prior single-row-per-guest design was hiding history (renewals updated in place, so `t_parking` only ever showed the *current* period and lost the per-renewal audit trail). (2) Dropped the `(property_id, vehicle_plate)` unique index — incompatible with the new design since the same plate can now have multiple rows over time. (3) Rebuilt `t_parking` from the two payment-of-truth tables: 24 `management_only=1` rows preserved verbatim with original `idrec`s; 231 new rows from paid `t_transactions` where `parking_fee > 0 AND parking_duration > 0` (bundled-with-room flow); 28 new rows from paid `t_parking_fee_transaction` (Finance > Parking Entry standalone flow). (4) Re-pointed `t_parking_fee_transaction.parking_id` to the matching new `t_parking.idrec` via a join on `(user_id, property_id, parking_type, order_id, start_rent, end_rent)` — 0 dangling references after. Final state: **283 rows, 68 currently active, 16 with `vehicle_plate='UNKNOWN'`** (those are bundled txns where no original `t_parking` row had a matching plate to backfill from — likely customers whose first booking with parking never wrote a t_parking row, or had it deleted). **Chart impact** — every Kost surfaced ~10× more active parking than before: Kost 1 cars 1/15 → 12/15, motorcycles 4/20 → 15/20; Kost 3 motorcycles 2/26 → 14/26; Kost 2 unchanged at 6/10 + 21/33 (same as post-sync). The bug wasn't Kost-2-only — same renewal-extension miss happened across every property; the manual-list audit just happened to be on Kost 2. **Rollback path**: `DROP TABLE t_parking; CREATE TABLE t_parking LIKE t_parking_single_line_old; INSERT INTO t_parking SELECT * FROM t_parking_single_line_old; ALTER TABLE t_parking ADD UNIQUE INDEX t_parking_property_id_vehicle_plate_unique (property_id, vehicle_plate);`. **Important: the code still has the old single-row update-in-place logic** in `BookingController::updatePaymentMethod` (Frontend web) and `Api/BookingController` (Mobile) — without a code change, future renewals will continue to update the existing row instead of inserting a new one, so the multi-row design will degrade back to single-row over time. Code fix is the immediate next step. **Production data + schema fix; staging unaffected (different DB).** |
